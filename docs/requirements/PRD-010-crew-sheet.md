## 1. Summary

When a runner publishes their plan, PlanUltra generates a **Crew Sheet** — a flat, static-feeling HTML page accessible to anyone with the link, with no login required. The page shows every aid station in sequential order with estimated arrival times, and at crew-accessible stations expands to show the runner's packing plan for the next segment and crew instructions.

The page is designed to be **printed** as a primary use case. Crew members in remote locations may not have reliable cell service; a printed A4/Letter sheet should be the fallback.

---

## 2. Publishing Lifecycle

### 2.1 Publish

The runner clicks "Publish crew sheet" in the app (Crew tab, PRD-007 §8). The system:

1. Generates a `crewShareToken` — a random 16-character URL-safe string (e.g. `xk7mQp2nRvTdWcLs`).
2. Stores `crewShareToken` and `crewPublishedAt` on the Race record in DynamoDB.
3. The crew sheet is served at `/crew/[crewShareToken]`.

The token is opaque — it must not encode the race ID or any user identifier.

### 2.2 Unpublish

The runner clicks "Unpublish" in the app. The system:

1. Clears `crewShareToken` and `crewPublishedAt` on the Race record (set both to `null`).
2. Any request to the old token URL returns **404**.
3. There is no "disable" state — the record is fully cleared.

### 2.3 Re-publish

Re-publishing generates a **new** `crewShareToken`. The old link becomes dead. The runner must re-share the new link. This is intentional — if a runner shares a link then wants to revoke access, unpublishing + re-publishing gives them a fresh link.

---

## 3. Route and Data Fetching

**Route:** `src/app/crew/[token]/page.tsx`

This is a server component. It fetches the race and all section data server-side using the token. No client-side data fetching.

```ts
// Pseudo-code for data fetch
const race = await getRaceByCrewToken(token)   // returns null if token not found
if (!race) notFound()

const sections = await getSectionsByRaceId(race.id)
```

The page renders fully on the server. There is no revalidation interval — this page is effectively static once rendered. If the runner updates their plan they must re-publish (which generates a new token) to push changes to crew. This keeps the implementation simple and avoids stale-read issues.

> **Future:** Consider ISR with a short revalidation window (60s) once live ETA updates are implemented (see §10.3).

## 6. Station List

A vertical sequence of aid station cards. Cards are separated by a thin connector line (Sky 30% opacity, 2px wide, centered) to visually represent the course as a flow.

Cards are ordered by `section.order`. The first card is always the race start; the last is always the finish.

## 9. Print Optimization

The page must print well on A4 and US Letter at default browser margins. Key rules:

```css
@media print {
  /* Hide interactive chrome */
  .print-hide { display: none !important; }

  /* Force white background on body */
  body { background: white; }

  /* Header: swap Midnight bg to Ridge Blue for ink saving */
  .crew-header { background: #1D7CBE !important; }

  /* Avoid page breaks inside station cards */
  .station-card { break-inside: avoid; page-break-inside: avoid; }

  /* Make crew-access cards stand out with a left border accent instead of background */
  .station-card--crew {
    background: white !important;
    border-left: 4px solid #1D7CBE !important;
  }

  /* Condition chips: print in grayscale-safe border style */
  .condition-chip { border: 1px solid #114574 !important; background: white !important; }

  /* Remove link underlines */
  a { text-decoration: none !important; color: inherit !important; }
}
```

The print button in the header (`window.print()`) is the primary affordance. No PDF generation server-side — the browser's native print dialog is sufficient.

## 10. Future Features (out of scope for this PRD)

These are explicitly deferred. Record them here so future PRDs can reference this as the origin.

### 10.1 Google Maps crew parking links

Each crew-access station card will eventually include a "Directions for crew" link that opens Google Maps to the crew parking coordinates for that aid station. The data model will need a `crewParkingCoords: { lat: number, lng: number } | null` field per section/aid station. UI: a small "📍 Crew parking" link below the station name.

### 10.2 Google Calendar events

A "Add to Google Calendar" link (or button) per crew-access station, pre-populated with the station name, estimated arrival time (with a ±buffer window), and crew parking location. Uses the Google Calendar URL API (`https://calendar.google.com/calendar/render?action=TEMPLATE&...`) — no OAuth required for the link format.

### 10.3 Live ETA updates

As the runner makes progress, their crew needs updated ETAs. Future implementation: the runner (or a pacer) marks sections complete in the app, which recalculates remaining ETAs and updates the crew sheet in near-real-time. This likely requires ISR revalidation or a Pusher/SSE channel rather than a static page.

### 10.4 Crew-access toggle per aid station

Currently `crewAccess` is a boolean field set at plan-build time. A future improvement allows the runner to toggle crew access per station from the Crew tab and have the crew sheet reflect it immediately.

## 13. Implementation Issues for Dev Agent

**Issue A — GSI for crew token lookup**
The crew token lookup requires a DynamoDB GSI. Define `GSI1` with `PK: CREW#<token>` at race creation/publish time. Do not do a full table scan.

**Issue B — Token generation**
Use `crypto.randomBytes(12).toString('base64url')` (Node.js built-in) to generate the 16-character URL-safe token. Do not use `Math.random()`.

**Issue C — Custom not-found page for crew token**
Do NOT use Next.js `notFound()` for crew token misses — that renders the generic app 404. Instead, handle the null case inline in `src/app/crew/[token]/page.tsx` and render the custom crew not-found UI described in §14.

**Issue D — Condition computation on server**
`suncalc` is a pure JS library that works in Node.js. Compute `lightConditions` server-side in the page component using the race's start datetime and coordinates. Do not push this to the client.

**Issue E — Print stylesheet**
Add `@media print` styles as a `<style>` block in the page component, not in `globals.css`. This keeps print styles co-located with the crew sheet page.

## 14. Crew Sheet Not-Found Page

When a crew token lookup returns `null` (token never existed, or the runner has unpublished), render a custom not-found UI instead of the generic 404. The page lives at `src/app/crew/[token]/page.tsx` — the token is available in props even on a miss, so the page can render contextually.

See reference mockup: `docs/requirements/mockups/crew-sheet-not-found.html`

### 14.1 Flavor text

The page uses running-flavored copy that acknowledges what happened without being terse. The headline rotates from a small set of options selected at render time (server-side, based on a hash of the token so it's stable on refresh):

| # | Headline | Subtext |
|---|---|---|
| 0 | "Looks like this crew sheet got lost somewhere out on the course." | "It may have been unpublished, or the link may have changed." |
| 1 | "Your crew sheet may have gotten lost between miles 44 and 62." | "Classic. The link may have been unpublished or regenerated." |
| 2 | "This link has gone dark — like mile 80 with a dying headlamp." | "The runner may have unpublished this plan or reshared a new link." |
| 3 | "Aid station closed. Nothing to see here." | "This crew sheet link is no longer active." |

Select variant: `parseInt(token.slice(-2), 36) % 4` — deterministic, no randomness needed at runtime.

### 14.3 HTTP status

The page should still return **HTTP 200**, not 404. Crew members may be on spotty cell networks — a 404 could cause some caching proxies to cache the error. A 200 with a clear human message is safer. The route simply renders the not-found UI when `getRaceByCrewToken` returns `null`.
