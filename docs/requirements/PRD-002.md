# PRD-002: Drop Bag Planner — "Plan" Tab
**Status:** Draft
**Created:** 2026-03-16
**Relates to:** PRD-001 (Phase 2 — Per-station gear & nutrition planning)

---

## 1. Summary

Add a "Plan" tab alongside the existing "Pace" tab on the race detail page. The Plan tab helps runners figure out what to pack in each drop bag by breaking the race into **sections** — where each section is the leg between one drop-bag station and the next. For each section, the runner sees the key contextual information they need to make packing decisions, and records what they intend to carry.

The goal is to reduce the cognitive load of drop bag packing, which today is done from memory, spreadsheets, or scratch paper, and is easy to get wrong.

---

## 2. Problem Being Solved

Drop bag packing requires a runner to mentally simulate the entire race leg-by-leg and answer a set of questions for each section: How far is it? How long will I be out there? How many times can I refill water? Will it be dark? Will it get significantly colder? Do I need a shoe change?

Each of these questions is answerable from data already in the system (GPX, pace estimates, weather forecast, aid station flags), but today a runner has to piece it together manually. A runner who packs 10 liquid IV packets when they only need 4 is carrying dead weight for miles. A runner who forgets a headlamp because they didn't track sunset timing ends the night in the dark.

---

## 3. Who Is This For?

Same primary user as PRD-001: the registered ultra marathon runner preparing for their race. This feature assumes they have already completed the Phase 1 setup — GPX uploaded, aid stations confirmed, pace entered — so arrival time estimates and weather data are available.

Runners most likely to benefit immediately: those running their first 100-miler, runners doing a race with 4+ drop bag stations, or anyone who has previously over- or under-packed a drop bag.

---

## 4. Core Concept: Sections

A **section** is defined as the leg from one drop-bag station to the next drop-bag station. The Start and Finish are always treated as drop-bag stations for this purpose (the Start is where you leave your crew; the Finish is the end). This means:

- A race with 3 drop-bag stations produces 4 sections: Start → DB1, DB1 → DB2, DB2 → DB3, DB3 → Finish.
- Aid stations between drop bag points that are NOT drop bag stations are **refill stops** — they matter for consumable counts but do not define section boundaries.
- If the runner has not flagged any stations as having drop bags (other than Start/Finish), the whole race is one section.

---

## 5. What Each Section Card Shows

Each section is presented as a card. The card is divided into two halves: **contextual information** (computed from existing data, read-only) and **runner inputs** (what the runner decides to pack).

### 5.1 Contextual Information (computed)

**Section header:**
- From station name → To station name
- Estimated departure time at the "from" station (from pace estimates)
- Estimated arrival time at the "to" station

**Distance and time:**
- Distance of this leg in miles (and km)
- Estimated time in section (hours and minutes)

**Refill opportunities:**
- Number of non-drop-bag aid stations within this section where the runner can refill water
- Displayed as a single number, e.g. "3 refill stops"
- This is the key multiplier for single-serve drink mixes and any other per-refill consumables

**Conditions — derived from weather and pace estimates:**
- Temperature at estimated departure from this section's start station
- Temperature at estimated arrival at this section's end station
- Temperature delta (e.g. "+8°F warmer" or "−14°F colder") to flag significant swings
- Whether sunset or sunrise occurs during this section (computed from estimated departure/arrival times vs. civil twilight for the race location and date)
- Night flag: is any part of this section expected to be run in darkness?

**Elevation summary:**
- Total elevation gain in this section (feet / metres)
- Total elevation loss in this section
- (Requires elevation data from GPX — displayed only if elevation data is present)

### 5.2 Runner Inputs (persisted)

These are the fields the runner fills in for each section. All inputs are saved to the database when the runner clicks Save (or auto-saved with debounce — TBD at implementation).

**Drink mixes:**
- Numerical input: how many single-serve drink mixes to pack
- Helper text: "You have {N} refill stops in this section" to anchor the decision
- The system does not auto-fill this — the runner decides based on their preference — but the refill count is the primary signal

**Calories:**
- Numerical input: calories-per-hour target (runner sets this once; it persists across sections as a default)
- Computed display: estimated total calories for this section = calories-per-hour × estimated section hours
- The runner can override the total for this specific section

**Gear checklist — boolean flags per section:**
- Headlamp (flagged automatically if any part of the section is in darkness, but overridable)
- Extra layer / jacket (runner's call — no auto-flag, but temperature delta is visible)
- Rain gear (runner's call — precipitation probability from weather is visible in context)
- Poles (runner's call)
- Shoe change at this drop bag (applies to the "from" station — do you want to change into fresh shoes before starting this section?)
- Trekking poles change / swap (same concept)

**Free-form notes:**
- One text field per section for anything that doesn't fit the structured fields — e.g. "pick up fresh socks", "swap headlamp batteries", "crew meeting point is at the fire road"

---

## 6. Drop Bag Summary View

Below the section cards, a "Drop Bag Summary" table consolidates what needs to be physically packed into each drop bag. A drop bag at station X contains the items for the section starting at X.

The summary table shows one row per drop-bag station with columns: drink mixes, estimated calories, headlamp (yes/no), extra layer (yes/no), rain gear (yes/no), shoe change (yes/no), notes. This is the view a runner would hand to their crew or use when physically packing bags before the race.

This view is read-only — it is derived entirely from the section inputs above and requires no additional data entry.

---

## 7. Relationship to Existing Systems

**Pace tab:** The Plan tab is a sibling tab, not a replacement. The Pace tab retains the aid station table and weather timeline as-is. Pace must be set before the Plan tab is fully functional — if no pace has been entered, the Plan tab shows a prompt to set pace first, since section times and weather context depend on arrival estimates.

**Aid station setup:** Drop-bag flags set on the setup page determine section boundaries. The Plan tab reads these flags but does not allow editing them — the runner goes back to the setup page to change which stations have drop bags.

**Weather system:** Temperature and precipitation data for each section are derived from the existing `RaceWeatherEntry[]` array (already computed by `alignWeatherToRace`). No new weather API calls are required. Sunset/sunrise is computed from the race start location and date using a civil twilight calculation — this does not require a weather API.

**Pace calculator:** Section times are derived from `ArrivalEstimate[]`. The section start and end arrival times define the window used to look up weather, compute time in section, and determine whether darkness occurs.

## 8. Data Model

Section plan data is persisted as a new record type in DynamoDB. Suggested shape:

```
PK: RACE#<raceId>
SK: SECTION#<fromStationOrder padded to 4 digits>

{
  raceId: string
  fromStationOrder: number       // order of the drop bag station that starts this section
  fromStationName: string
  toStationName: string
  drinkMixes: number | null
  caloriesPerHour: number | null // runner's target; null means not set
  caloriesOverride: number | null // if runner manually overrides the computed total
  hasHeadlamp: boolean
  hasExtraLayer: boolean
  hasRainGear: boolean
  hasPoles: boolean
  shoeChange: boolean
  notes: string
  updatedAt: string              // ISO 8601
}
```

One record per section per race. Section identity is keyed by the `fromStationOrder` of the starting drop-bag station (consistent with the existing aid station key scheme).

The race-level calories-per-hour default is stored on the Race record itself (a new `caloriesPerHour` field), not on section records. Section records store only a per-section override (`caloriesOverride`). This means changing the race-level default updates the computed calorie totals for all sections that haven't been individually overridden.

**Cascade delete:** When a race is deleted, all associated data must be deleted in the same operation: the Race record, all `AID#` records for that race, and all `SECTION#` records for that race. The delete function must query and remove all three record types. This mirrors the existing requirement to pair `deleteRace` with `deleteAidStations`, extended to include sections.

---

## 9. What This Feature Does Not Do

- Does not prescribe what to pack. It surfaces contextual data and provides structured fields; the runner makes all packing decisions.
- Does not track specific food items, brands, or calorie counts per item. Nutrition is a single "total calories" number per section.
- Does not account for calories available at aid stations. The assumption is the runner is planning what to carry from drop bag to drop bag, not optimising against what the race provides.
- Does not generate a physical packing list document (printable list, PDF, etc.) — that is a future enhancement.
- Does not support crew-specific instructions on this tab. Crew coordination is a separate planned feature.
- Does not support multiple runners sharing a plan.
- Does not auto-populate gear flags based on weather thresholds. Weather data is surfaced as context; the runner makes the call.
- Does not validate that the runner's drink mix count matches the number of refill stops. The refill count is informational, not prescriptive.

---

## 10. Open Questions

- **Sunset/sunrise computation:** Civil twilight calculation needs the race latitude/longitude (available from the GPX start point) and the date. A lightweight JS library (e.g. `suncalc`) handles this without an API call — this is the recommended approach.
- **Elevation data availability:** Elevation gain/loss per section requires that the GPX contains `<ele>` tags on track points, which most modern GPS devices include but is not guaranteed. The section card should gracefully omit elevation data if not present rather than showing zeros.
- **Tab state when no pace is set:** Show the section structure with contextual data fields greyed out / showing "—" where pace-dependent data is missing, with a banner prompting the runner to set pace. The tab is always visible and navigable — the missing-pace state will be revisited when pace persistence is addressed.

---

## 11. Decisions Log

| Decision | Choice | Rationale |
|---|---|---|
| Section boundaries | Drop-bag stations only (not every aid station) | Matches the physical logistics reality — a runner only has the option to add or remove items at drop bag stations |
| Non-drop-bag aid stations | Shown as refill stop count per section | The number of refills is a direct multiplier for single-serve drink mixes; more useful than listing individual stations |
| Nutrition granularity | Total calories per section via calories-per-hour input | Balances utility with simplicity; item-level tracking is out of scope |
| Persistence | DynamoDB auto-save (debounced), new `SECTION#` record type | Plan data must survive page reloads; auto-save removes friction vs. explicit save button |
| Calories-per-hour default | Stored on Race record; per-section override on Section record | Set once, applies to all sections; overridable per section without resetting the race default |
| Cascade delete | Race deletion must also delete all `AID#` and `SECTION#` records | Prevents orphaned data; enforced at the application layer in the delete function |
| Weather data source | Reuse existing `RaceWeatherEntry[]` | No new API calls; weather is already fetched and aligned to runner position |
| Sunset/sunrise | Compute client-side via suncalc or equivalent | No API needed; lat/lon and date are available |
| Gear flags | Boolean per section, no auto-population from weather thresholds | Avoids false confidence; runner is responsible for their own gear decisions |
| Tab visibility with no pace | Show tab with "—" placeholders and a set-pace banner | Keeps the feature discoverable; missing-pace UX to be revisited when pace persistence is added |
