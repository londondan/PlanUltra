# PRD-004: Weather Timeline — Fix and Redesign
**Status:** Draft — Visualization spec superseded by Section 11 (v2)
**Created:** 2026-03-16
**Relates to:** `src/lib/weather-timeline.ts`, `src/components/WeatherTimeline.tsx`

---

## 1. Summary

The weather feature is currently broken and the UI, even when it works, does not serve the runner's actual needs. This PRD covers two things in sequence: fixing the broken data pipeline first, then replacing the existing column-card UI with a purpose-built race weather visualization that shows the entire race at a glance.

---

## 2. What's Currently Broken

### Bug: `interpolateRunnerDistance` divide-by-zero

In `src/lib/weather-timeline.ts`, the "before first station" branch is broken:

```typescript
// BROKEN — divides by zero, always returns 0
if (time <= estimates[0].estimatedArrival) {
  const ratio =
    (time.getTime() - estimates[0].estimatedArrival.getTime()) /
    (estimates[0].estimatedArrival.getTime() - estimates[0].estimatedArrival.getTime() || 1)
  return 0
}
```

The denominator is always `0` (same value minus itself), saved only by the `|| 1` fallback, which means `ratio` is always `0` and this branch always returns `0`. The `return 0` at the end of the branch is unconditional anyway, so the entire ratio calculation is dead code. The correct fix is to simply return `0` directly — the runner is at the start, so distance from start is zero.

This bug means any forecast hour that falls between race start and the first aid station's estimated arrival gets position `(trackPoints[0].lat, trackPoints[0].lon)` rather than an interpolated position. For a race starting at 5am with the first aid station at mile 15 (roughly 4 hours into the race), that's the first ~4 weather hours all pinned to the start coordinates. This is actually not catastrophically wrong for weather (the weather at mile 0 vs mile 15 is similar for most forecasting granularity), but it needs to be fixed for correctness and to unblock the larger interpolation logic.

### Missing: the component renders nothing when pace is not set

The component returns an empty-state prompt when `entries.length === 0`. This is correct behavior, but the empty state is easy to miss on the page. This is a UX issue, not a bug — addressed in the redesign below.

### Missing: the weather fetch is called server-side in a client component

In `src/app/dashboard/[raceId]/page.tsx`, `fetchForecast` is called inside a `useEffect`. This is correct (client-side fetch). However, the `fetch` call happens directly from the browser to `api.open-meteo.com` — which means it is subject to CORS, network conditions, and no server-side caching. This is not broken but is a known fragility. It is noted here but not in scope for this PRD to fix — that is a future infrastructure improvement.

## 3. The New Visualization

### Core principle: race at a glance

The existing UI is a horizontal scrolling row of 80px cards — one per hour. For a 28-hour race, that is 28 cards. You cannot see the whole race at once. The runner has to scroll to understand the arc of conditions across the event. This defeats the primary purpose: helping a runner mentally prepare for what's coming.

The new visualization is a **horizontal timeline bar** that spans the full race window in a single fixed-width view. The runner sees the whole race — start to finish — without scrolling. Individual hour precision is sacrificed in favor of pattern recognition: is it getting colder in the back half? when does night hit? is there a rain window around hour 18?

### Layout

The component is a single card, fixed to the full content width. Internally it is composed of stacked horizontal rows, all sharing the same time axis:

```
┌─────────────────────────────────────────────────────────────────────┐
│  WEATHER OVERVIEW                              103.4 mi · ~28h      │
│                                                                     │
│  [time axis: 5am Sat ... 5am Sun ... 9am Sun]                      │
│                                                                     │
│  TEMP    ░░▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓████████████████▓▓▓▓▓▓▓▓░░░░ (gradient) │
│          48°F                                           71°F        │
│                                                                     │
│  LIGHT   [day][day][day][night][night][night][night][day][day]      │
│                                                                     │
│  PRECIP  ░░░░░░░░░░░░░░████████░░░░░░░░░░░░░░░░░░░░░░░░░░ (bars)   │
│                                                                     │
│  ──────────────────────────────────────────────────────────────     │
│  [●Flint Mill 15mi 8am] [●Jennings Creek 34mi 11am] [●Finish 103mi]│
└─────────────────────────────────────────────────────────────────────┘
```

### Row 1: Time axis

- Displays clock times at regular intervals (every 2–4 hours depending on race length)
- Shows day/date change label (e.g. "— Sun —") when the calendar date rolls over
- Tick marks align with all other rows

### Row 2: Temperature gradient bar

- A continuous horizontal gradient bar where color encodes temperature
- Cold end: Sky blue (`#82C7F6`) — cool temperatures
- Warm end: a warm amber/orange — hot temperatures
- The gradient is computed from the actual temperature range across the race window — the coldest hour maps to the cold color, the hottest to the warm color
- Overlaid on the bar: the min and max temperature labels at their positions
- The bar height is ~24px

This is the key insight: the runner does not need to know it was 58°F at hour 7. They need to see that it gets significantly colder between hour 14 and hour 22, then warms again. The gradient encodes that pattern instantly.

### Row 3: Daylight bar

- A segmented bar: dark segments for night hours, light segments for day hours
- Night: Deep Ridge `#114574` fill with a moon icon at the start of each night segment
- Day: Mist `#DBF1FA` fill with a sun icon at the start of each day segment
- Height ~20px, same width as the temperature bar
- This row directly answers "when will I be running in the dark?" — one of the most critical planning questions for ultra runners

### Row 4: Precipitation bar

- A bar chart where each hour-column's height represents precipitation probability
- 0% = no bar. 100% = full height of the row area (~32px)
- Bar color: Ridge Blue `#1D7CBE` at 70% opacity for light precip, deepening toward Deep Ridge `#114574` for high probability
- A threshold line at 30% precipitation probability — bars crossing this line get a slightly more intense color, signaling "worth paying attention to"
- Hours with 0% probability show nothing — no visual noise

### Row 5: Aid station markers

- A thin horizontal rule
- At the x-position corresponding to each **major aid station** (drop bag or crew access), a vertical tick mark and label
- Label shows: station name, distance (miles), and estimated arrival time
- Start and Finish are always shown
- Non-major stations (water-only, no drop bag, no crew access) are not shown — this view is for logistics planning, not route description
- Labels are short and abbreviated to avoid collision; on hover a tooltip shows the full name and time

---

## 4. What "Major Aid Station" Means for This View

The weather timeline shows only aid stations where `hasDropBag === true` OR `hasCrewAccess === true`, plus Start and Finish. This is consistent with how sections are defined in PRD-002. The visual rationale: these are the decision points in a race — where a runner has real options to change gear, refuel seriously, or meet crew. The weather pattern between these points is what drives packing decisions.

## 5. Component Interface

The component signature expands from the current:

```typescript
// Current
interface WeatherTimelineProps {
  entries: RaceWeatherEntry[]
  forecastAvailable?: boolean
  unavailableReason?: string
}
```

To:

```typescript
// New
interface WeatherTimelineProps {
  entries: RaceWeatherEntry[]
  aidStations: AidStation[]          // full list — component filters to major stations
  arrivalEstimates: ArrivalEstimate[] // for positioning stations on the time axis
  raceStart: Date
  totalDistanceMiles: number
  forecastAvailable?: boolean
  unavailableReason?: string
}
```

The component receives the full aid station list and filters internally to `hasDropBag || hasCrewAccess || isStart || isFinish`. This keeps the filter logic inside the component where it belongs.

---

## 6. Empty and Unavailable States

**No pace set (entries empty):** Show the component shell with the time axis and aid station row rendered (these don't need pace), but replace the temperature/daylight/precipitation rows with a muted placeholder bar and the message "Set your pace above to see weather aligned to your race." This makes the component feel present and useful rather than hidden.

**Race more than 16 days out:** Show the full component shell with a banner at the top: "Weather forecast available within 16 days of your race. Check back closer to race day." The aid station row is still shown since it doesn't depend on weather data.

**Weather fetch failed silently:** Currently errors are swallowed with a comment. The component should receive an explicit `forecastAvailable: false` with reason `"Weather data unavailable — check your connection."` rather than just receiving an empty entries array with no explanation.

## 7. Fixes Required (Implementation Order)

These should be done in order — the bug fix first, then the UI rebuild.

### Fix 1: `weather-timeline.ts` — interpolation bug

Replace the broken "before first station" branch:

```typescript
// Before fix (broken)
if (time <= estimates[0].estimatedArrival) {
  const ratio = ... / (... - ... || 1)  // always 0
  return 0
}

// After fix
if (time <= estimates[0].estimatedArrival) {
  return 0  // runner hasn't left the start yet
}
```

### Fix 2: `weather-timeline.ts` — interpolation uses elapsed minutes incorrectly

The distance interpolation between stations uses `elapsedMinutes` divided by total elapsed to scale distance. This is an approximation that works for flat pace but will break for grade-adjusted pace in Phase 2. It should instead use `station.distanceFromStart` directly from the `AidStation` records. However, `ArrivalEstimate` doesn't currently carry `distanceFromStart`. Two options:

- Option A: Add `distanceFromStart` to `ArrivalEstimate` (preferred — cleaner interface)
- Option B: Pass the full `AidStation[]` array alongside `ArrivalEstimate[]` to `alignWeatherToRace`

This is a minor refactor, not a blocker. The current approximation is close enough for flat pace. Flag as a known limitation in the spec, fix alongside the Phase 2 pace upgrade.

### Fix 3: `WeatherTimeline.tsx` — rebuild as race-overview visualization

Full replacement of the scrolling column-card UI with the horizontal timeline bar described in Section 3. Implemented as an SVG or a combination of CSS flexbox rows with absolute-positioned elements sharing a common time-axis scale function.

The SVG approach is recommended: a single `<svg>` element with a shared x-scale makes it straightforward to position all rows on the same time axis without CSS width calculation hacks.

## 8. What This Feature Does Not Do

- Does not show wind speed in the new visualization. Wind is relevant for exposed ridgelines but is secondary to temperature, daylight, and precipitation for planning purposes. It remains available in the raw data for a future "detail on hover" interaction.
- Does not show per-hour exact temperatures as labels — only the gradient encoding and min/max anchors.
- Does not forecast for individual aid station locations — the weather data is fetched once for the race start coordinates and applied across the full course. This is a known limitation documented in the weather system spec.
- Does not allow the runner to tap a section of the timeline to see a breakdown — that level of detail is a future enhancement.
- Does not cache weather data between page loads.

## 11. Visualization v2 — Line Graph (supersedes Section 3)
**Added:** 2026-03-17
**Reason:** The gradient bar encoding from Section 3 was implemented and reviewed. The decision was made to replace it with a line graph approach that communicates the same information more precisely — temperature as a curve the runner can read quantitatively, daylight as a second overlaid curve on the same y-axis, and precipitation as background shading rather than a separate bar row.

### 11.1 Core principle (unchanged)

The whole race at a glance — no scrolling. The x-axis is time, spanning from race start to estimated finish. Everything is anchored to that shared axis.

### 11.2 Overall layout

One SVG, full content width. Three logical layers rendered in order (back to front):

```
┌──────────────────────────────────────────────────────────────────┐
│  WEATHER OVERVIEW                             103.4 mi · ~28h    │
│                                                                  │
│  90°F ┤                                                          │
│       │         ╭──────╮                                         │
│  70°F ┤   ╭─────╯  71° │╲                      ← temperature     │
│       │  ╱             │  ╲                                      │
│  55°F ┤ ╱           min│   ╲──────────── 55°                     │
│       │╱            55°│                                         │
│  40°F ┤                │                                         │
│       │                                                          │
│  1.0  ┤──────────────────╲        ╭────────── ← daylight (0–1)   │
│       │  ☀️ Sunrise 6:14a  ╲      ╱  ☀️ Sunrise 6:15a            │
│  0.0  ┤                    ╲────╱   🌙 Sunset 8:47p              │
│       │                                                          │
│  [░░░░░░░░░░░░░░░░░░░░░░░░░] ← precip shading behind lines       │
│                                                                  │
│  ─────────────────────────────────────────────────────────────── │
│  [●Start 5:00a] [●Flint Mill 15mi 10:03a] [●Finish 103mi 9:32a] │
└──────────────────────────────────────────────────────────────────┘
```

### 11.3 Layer 1 (background): Precipitation shading

Rendered first so it sits behind both line graphs.

- For each hour where `precipitationProbability > 0`, fill the full chart height at that x-position with a vertical band
- Fill color: Ridge Blue `#1D7CBE`
- Opacity scales with probability: `opacity = precipitationProbability / 100 * 0.25` — so 100% probability = 25% opacity, 30% = 7.5% opacity
- This keeps the shading clearly subordinate to the line graphs while still making rain windows visible as a wash
- No axis, no labels, no threshold line — the shading is ambient context, not a precise readout
- Hours with 0% probability contribute no shading (transparent)

The effect: rain windows appear as soft blue washes behind the temperature curve. A runner glancing at the chart immediately sees "there's a blue patch around hour 14 — that's when rain is likely."

### 11.4 Layer 2: Temperature line graph

**Y-axis:** Temperature in °F. Range is padded: `[minTemp - 5, maxTemp + 5]`, so the line never touches the top or bottom edge of the chart area.

**Line style:**
- Stroke: Ridge Blue `#1D7CBE`, stroke-width 2.5
- No fill under the line (pure line, no area fill)
- Smooth curve: use SVG cubic bezier via a cardinal spline through the hourly data points

**Y-axis labels:**
- Left side, 3–4 tick labels at round numbers (e.g. 40°, 55°, 70°, 85°)
- Font: Geist Sans, 10px, Deep Ridge color
- Tick lines: faint horizontal rules across the chart, `rgba(130,199,246,0.2)`, 1px

**Min/max annotations:**
- At the x-position of the minimum temperature hour: a small dot on the line (4px radius, Ridge Blue fill) with a label below: `55°F` in Geist Mono 11px, Ridge Blue
- At the x-position of the maximum temperature hour: same treatment, label above: `71°F`
- If min and max are within 60px of each other on the x-axis, offset one label vertically to avoid overlap

### 11.5 Layer 3: Daylight line graph

Overlaid on the same SVG and same x-axis as the temperature line. Uses a **separate y-axis on the right side** — but the y-axis is implicit (no tick labels shown), since the values are binary: the line is either at the top (day) or bottom (night) of its band.

**Value encoding:** `isNight` from `RaceWeatherEntry`:
- Day (`isNight === false`): plot at y = top of daylight band
- Night (`isNight === true`): plot at y = bottom of daylight band
- Transition between adjacent hours of different day/night state: draw a steep diagonal connecting the two positions — this approximates the actual sunrise/sunset moment

**Daylight band:** occupies the bottom 20% of the chart area, visually separated from the temperature area with a faint horizontal guide line.

**Line style:**
- Stroke: Sky `#82C7F6`, stroke-width 2
- The line is a step-with-diagonal — flat at top, steep drop at sunset, flat at bottom, steep rise at sunrise

**Sunrise / sunset intersection labels:**
- Detect every transition point where `isNight` changes between adjacent hours
- At each transition: place a vertical tick mark on the daylight line
- Label format:
  - Sunset: `🌙 8:47p` — label positioned above the line, left-anchored to the tick
  - Sunrise: `☀️ 6:14a` — label positioned above the line, left-anchored to the tick
- Font: Geist Sans 10px, Midnight color
- If two transitions are within 80px on the x-axis (very short day or night), use abbreviated labels and offset vertically

**Note on precision:** The `isNight` field in `RaceWeatherEntry` is already computed hourly by Open-Meteo. The transition point is inferred as the midpoint between the last hour before and the first hour after the state change — this gives ~30-minute precision on sunrise/sunset, which is sufficient for race planning.

### 11.6 X-axis (time axis)

- Shared across all layers — sits at the bottom of the chart area, above the aid station row
- Tick marks every 2h (races ≤ 24h), 4h (races 25–48h), or 6h (races > 48h)
- Labels: Geist Sans 9px, Deep Ridge at 70% opacity
- Date-change markers: when the clock rolls past midnight, show the day abbreviation (e.g. "Sun") in Geist Sans 9px bold, Ridge Blue — sits above the tick, replacing the time label for that tick

### 11.7 Aid station row (unchanged from v1)

Below the chart area, separated by a 1px Sky rule. Same behavior as specified in Section 3:
- Only major stations (drop bag, crew access, Start, Finish)
- Vertical tick + dot at x-position of estimated arrival time
- Name, distance in miles, estimated arrival time
- Alternating above/below label placement to reduce crowding

### 11.10 What changes vs. the v1 implementation

The v1 component (`WeatherTimeline.tsx`) was built per Section 3 and is currently in the codebase. The following elements are **removed** in v2:

| v1 element | v2 replacement |
|---|---|
| Temperature gradient bar (colored rectangle) | Temperature line graph |
| Daylight segmented bar (filled rectangles) | Daylight step line with intersection labels |
| Precipitation bar chart (vertical bars) | Background precipitation shading (opacity-scaled wash) |
| Separate row-per-layer layout | All three data layers share one chart area |

The component interface (Section 5) is **unchanged** — same props, no new data requirements. All v2 changes are internal to `WeatherTimeline.tsx`.

### 11.11 Decisions (v2)

| Decision | Choice | Rationale |
|---|---|---|
| Line graph vs. gradient bar for temperature | Line graph | More precise — runner can read "it drops from 71° to 55° between hour 10 and hour 18" directly from the curve shape. Gradient bar only conveys relative warmth, not magnitude. |
| Daylight on same axis as temperature | Yes, separate y-scale in bottom band | Keeps both data series in one eyeful. Runner sees "the temperature drops right as night begins" as a visual correlation. Separate chart would break that connection. |
| Precipitation as background shading, not bars | Background wash | Bars compete with the line graphs for attention and imply more precision than Open-Meteo's hourly probability warrants. A wash says "this window is risky" without overstating certainty. |
| Sunrise/sunset labeled at intersection | Yes, with time | The exact moment matters for gear decisions — "do I need a headlamp for the Flint Mill aid station?" requires knowing whether sunset is before or after that time. |
| Daylight line is a step-with-diagonal, not smooth | Yes | A smooth bezier curve would imply gradual dimming, which is not what the data represents. The steep diagonal at sunrise/sunset is visually honest about the binary day/night encoding. |
| No fill under temperature line | Correct — pure line | Area fill adds visual weight that competes with the precipitation shading layer underneath. |
